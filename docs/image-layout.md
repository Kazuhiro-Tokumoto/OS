# ディスクイメージの構成

起動に必要なものは全部 `build/myos.img` 1 個に入る。
ブートローダー・カーネル・ルートファイルシステムを別のメディアに分けない。
そのまま USB メモリに `dd` すれば起動する。

```
LBA 0            stage1 (MBR + パーティションテーブル)
LBA 1  - 17      stage2_linux
LBA 20           ペイロードテーブル ("MYOSPLD2")
LBA 64 -         bzImage の setup 部
LBA    -         bzImage の本体 (プロテクトモード用)
LBA    -         initramfs (使う場合)
LBA 26624 -      ext4 のルートファイルシステム  → /dev/sda2
```

パーティションテーブル:

| # | 種別 | 内容 |
| --- | --- | --- |
| 1 | 0x83 (bootable) | ブート領域（stage1/stage2/カーネル） |
| 2 | 0x83 | ext4 のルートファイルシステム |

BIOS 的にはパーティションテーブルが無くても起動できる実装が多いが、
無いと拒む BIOS もあるので付けている。Stage1 のコードは `0x1BE` より
手前に収まっているので、テーブルと衝突しない。

## なぜ 2048 バイト境界に揃えるのか

ペイロード（カーネルの setup 部・本体・initramfs）はすべて
**512 バイト LBA が 4 の倍数**になる位置に置いてある。

最終目標が ISO（CD / USB 両対応のインストールメディア）だから。
CD から起動するとき `INT 13h` は **2048 バイト単位でしか読めない**ので、
最初からその境界に乗る置き方にしておけば、ISO を作る段になって
配置をやり直さずに済む。

ペイロードテーブル自体も LBA 20（= 10240 バイト = 2048 × 5）に置いてある。

## なぜ bzImage を 2 つに割るのか

`bzImage` は「setup 部」と「プロテクトモード用の本体」が繋がった 1 個の
ファイルで、本体は先頭から `(setup_sects + 1) * 512` バイト目から始まる。

これを 1 つの塊のままイメージに置くと、**本体の開始位置が `setup_sects`
次第で 2048 バイト境界からずれる**。`setup_sects` はカーネルのビルド内容で
変わる（今回は 39）ので、当てにできない。

そこで `tools/build_image.py` がビルド時に 2 つへ割り、それぞれを
2048 バイト境界に置いて、位置をペイロードテーブルに記録している。
おかげでブートローダー側は `setup_sects` から位置を計算する必要がなくなり、
処理も短くなった。

## ペイロードテーブル (LBA 20)

`tools/build_image.py` が書き、`src/boot/stage2_linux.asm` が読む。

| オフセット | 内容 |
| --- | --- |
| `0x00` | マジック `"MYOSPLD2"` (8 バイト) |
| `0x08` | setup 部の LBA |
| `0x0C` | setup 部のセクタ数 |
| `0x10` | 本体の LBA |
| `0x14` | 本体のセクタ数 |
| `0x18` | 本体のバイト数 |
| `0x1C` | initramfs の LBA |
| `0x20` | initramfs のセクタ数 |
| `0x24` | initramfs のバイト数 |
| `0x28` | カーネルコマンドライン (0 終端) |

## Stage2 は「もう載っているか」を自分で見分ける

Stage2 はオフセット 3 に `'MYS2'` という目印を持っている。
Stage1 は `0x7E00 + 3` を見て、既にその目印があれば**ディスクからの
読み込みを省く**。

CD（El Torito のノーエミュレーション起動）では、BIOS が
stage1 と stage2 をまとめて `0x7C00` に読み込んでくれる。
そのとき stage2 はちょうど `0x7E00` に載るので、読み直す必要がない。
逆に USB / HDD からの起動では目印が無いので、普通に読みに行く。

1 つのコードでどちらのメディアにも対応できる。

## ルートファイルシステム

`tools/build_rootfs.sh` が debootstrap で Debian bookworm の最小構成を作り、
Xorg と Firefox ESR を入れる。`tools/make_rootfs_img.sh` が
`mkfs.ext4 -d` でそれを ext4 イメージに固める（マウント不要なので
コンテナや CI の中でも作れる）。

### なぜ initramfs だけで済ませないのか

Firefox は素のフレームバッファでは動かない。X11 と大量の共有ライブラリを
要求する。引き継ぎ資料の方針
「動的リンカーも共有ライブラリも自作せず、既存の glibc をそのまま流用する」
を素直に実行するなら、既存ディストリのルートをそのまま土台にするのが早い。

### systemd は使わない

カーネルには `init=/myos-init` を渡している。`/myos-init` は
`/proc` `/sys` `/dev` などを自分でマウントしてから X を起動するだけの
シェルスクリプト。起動が速く、何が動いているか把握しやすい。
